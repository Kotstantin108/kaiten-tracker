# Гейты сдачи работы

Код — `src/core/review-gates.ts` (решения и тексты отказов),
`src/kaiten-verify.ts` (команда `kaiten verify`, git и запуск проверок),
`src/core/skeleton.ts` («Как проверить»), `src/config.ts` (настройки).

## Зачем

Агенты пишут код быстрее, чем люди успевают его читать. У сдачи работы был
один гейт: `kaiten review` проверял отметки критериев, запись в журнале и
«Было / Стало». Запускались ли проверки проекта и обновлена ли документация,
он не знал: «тесты прошли» в журнале оставалось словами агента.

Теперь проект называет в `kaiten.json`, без чего работу сдавать нельзя, а
проверяет это инструмент. Всё выключено, пока проект не включил: без ключей
`review` и `domains` команды ведут себя как раньше.

## Настройки проекта

В корне `kaiten.json` репозитория задач:

```json
{
  "review": {
    "checks": [
      { "name": "typecheck", "run": "npm run typecheck" },
      { "name": "lint", "run": "npm run lint" },
      { "name": "test", "run": "npm run test", "timeoutMin": 20 }
    ],
    "docs": ["docs/**", "**/README.md"],
    "testPlan": true
  },
  "domains": {
    "core": "человек читает изменения целиком",
    "supporting": "автор и гейты",
    "generic": "пролистать после гейтов"
  }
}
```

| Ключ | Что включает |
|---|---|
| `review.checks` | проверки перед ревью: `name` — имя для журнала и сообщений, `run` — команда оболочки в корне репозитория кода, `timeoutMin` — предел времени (по умолчанию 30 минут) |
| `review.docs` | пути документации: в изменениях ветки задачи должен быть файл под ними. `*` — внутри папки, `**` — через папки, папка без звёздочек — всё, что в ней |
| `review.testPlan` | раздел «Как проверить» обязателен в постановке story |
| `domains` | домены задач: имя (латиница, цифры, дефис) → правило ревью |

У репозиториев одного проекта проверки разные — свои задаются у репозитория и
заменяют общие по каждому ключу:

```json
"repos": [
  { "name": "acme-app", "label": "Acme-app" },
  { "name": "acme-site", "label": "Acme-site", "review": { "checks": [{ "name": "build", "run": "npm run build" }] } }
]
```

Гейты проверок и документации действуют на story, tech и bug. У спайка
результат — ответ, а не код; эпик на ревью не сдают.

## Проверки: `kaiten verify`

```bash
git commit …              # сначала коммит
kaiten verify PRJ-123     # прогон проверок проекта на этом коммите
kaiten review PRJ-123     # принимает только с успешным прогоном на текущем коммите
```

`kaiten verify` запускает проверки по порядку и останавливается на первой
упавшей. Итог пишет в задачу:

- в шапку — свидетельство `checks`: хеш коммита, прошли ли все, имена
  проверок;
- в журнал — запись для людей: `проверки пройдены: typecheck — прошла (12 с),
  test — прошла (48 с); коммит a1b2c3d4e5` или `проверки не пройдены: … lint —
  не прошла (3 с), test — не запускалась; …`.

Вывод упавшей проверки команда показывает агенту — последние 40 строк, не
больше 4000 знаков. В журнал он не попадает: в выводе бывают секреты
окружения, а журнал открыт по ссылке из карточки.

`kaiten review` отказывает и называет команду, если:

- проверки по задаче не запускались;
- они шли на другом коммите — коммит после прогона его обесценивает;
- на текущем коммите они не прошли;
- в рабочей копии есть незакоммиченное;
- у проекта появилась проверка, которой в прогоне не было.

### Почему свидетельство — поле задачи, а не запись в журнале

Запись в журнале — текст: такую же строку агент напишет через `kaiten log`.
Поле `checks` принадлежит CLI, как `tracker` или `branch`: `kaiten edit`
отклоняет правку, которая его меняет, а ставит его одна операция —
`kaiten verify`. Запись в журнале остаётся для людей; `kaiten review` смотрит
только на поле.

Привязка к коммиту — потому что проверяется то, что уйдёт на ревью. Отсюда
правила прогона:

- только на чистой рабочей копии (изменённые и новые файлы — отказ; лишнее —
  в `.gitignore`);
- только на ветке задачи и из её репозитория;
- проверка, которая сама изменила файлы репозитория (автоисправление линтера,
  обновление снимков), свидетельства не даёт: прогон не засчитывается, пока
  изменения не закоммичены. Результаты сборки и покрытие держите в
  `.gitignore`;
- повторный `kaiten verify` на том же коммите проверки заново не гоняет.

Что запускать, называет только `kaiten.json` репозитория задач. Строку команды
из аргументов или из текста задачи инструмент не исполняет, поэтому агент не
может подменить проверку на пустую. Гейт локальный: CI он не запускает и
статусы CI не читает.

## Документация

`kaiten review` смотрит файлы, изменённые в ветке задачи от общего предка с
основной веткой репозитория (`repos[].branch`, с сервера — `origin/<ветка>`,
если она там есть) до `HEAD`. Ни одного файла под путями `review.docs` — отказ
с двумя выходами: обновить страницу модуля, который меняли, или сказать,
почему документация не меняется:

```bash
kaiten review PRJ-123 --no-ingest "правка опечатки в тексте кнопки"
```

Причина попадает в журнал задачи (`документация не обновлена: …`), как у
`--no-visual` и `--unchecked`. Правка есть — в журнале названы файлы
(`документация: docs/orders.md`). `--no-ingest` при правленой документации —
отказ: правка и есть ответ.

Документацию `review` проверяет раньше проверок: её правка — новый коммит,
после которого проверки всё равно гнать заново.

## «Как проверить»

С `review.testPlan` шаблон `kaiten new --type story` получает раздел «Как
проверить» перед «Шаги»: какие интеграционные тесты добавить или изменить и
как проверить результат как чёрный ящик, не читая код. Без непустого раздела
команда отказывает — как без критериев. Проверять нечего:

```bash
kaiten new "…" --type story --no-test-plan "меняется только текст кнопки" …
```

Причина записывается в раздел строкой «Проверять нечего: …».

Требует раздел только `kaiten new`. Линтер, `show`, `start`, `review`, `done`
и `edit` о нём не знают: задачи, заведённые раньше, остаются рабочими.

## Домен задачи

Домен — поле задачи `domain` из списка проекта:

- задаётся при `kaiten new --domain <имя>`, правится в тексте задачи
  (`kaiten edit`); неизвестное имя — отказ со списком допустимых;
- виден в шапке `kaiten show` вместе с правилом ревью и в строке
  `kaiten list`;
- `kaiten review` пишет его в запись о сдаче рядом с веткой и коммитом:
  `на ревью: ветка …, коммит …; домен core — человек читает изменения целиком`;
- в карточке Kaiten — поле-выбор «Домен» (после `pnpm run setup`). Владелец
  значения — файл задачи: синхронизация пишет его в карточку, когда домен в
  задаче есть; у задачи без домена поле карточки не трогает.

Домен необязателен: задачи из интерфейса Kaiten приходят без него, и
`kaiten new` его не требует. Кто какие изменения читает — правило проекта;
инструмент домен только хранит и показывает. Проект без `domains` поля не
видит нигде.

## Включение

1. Обновить `kaiten` на всех машинах: новые поля задач (`checks`, `domain`)
   старые версии не читают. `SYNC_VERSION` 7 заставит их обновиться самих при
   первой синхронизации; зависимости не менялись, переустановка не нужна.
2. Добавить ключи в `kaiten.json` и отправить. Проверки, документация и «Как
   проверить» действуют сразу, как только задачи обновятся на машине
   (`kaiten pull`).
3. Для поля «Домен» в карточках — `pnpm run setup` (план → `--apply`) и
   отправить `kaiten.json` с `mapping.domainProperty`. Без этого домен живёт
   в задачах и в выводе `kaiten`, в карточку не пишется.
4. Обновить копию скилла в репозиториях кода: `pnpm run connect-repo`.

Перед включением проверок убедитесь, что они проходят на основной ветке и не
меняют файлы репозитория: иначе первая же сдача упрётся в гейт.
