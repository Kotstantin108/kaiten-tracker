# Находки

Решения согласованы с владельцем 12.11.2026. Код — `src/core/found.ts`
(чистая часть), `src/kaiten-found.ts` (команда и фоновая очередь),
`src/found-investigate.ts` (снимок и запуск модели), `src/found.ts` (скрипт
владельца).

## Зачем

Агент, занятый своей задачей, замечает дефекты рядом. Раньше он сразу заводил
задачу — посреди большой работы, с чужим контекстом и недоделанным кодом перед
глазами. Задачам в Kaiten верят: младшие разработчики брали их в работу, а
«Можно младшему» агент выдавал себе сам, написав «Нет» в трёх разделах.

Теперь запись находки отделена от постановки задачи, а между находкой и
младшим стоят два фильтра: исследование с чистым контекстом и разбор человеком.

## Путь находки

1. **Заметка.** `kaiten found "<что не так>" --where … --why … [--from
   <задача>]` пишет файл `findings/<id>.md` в репозиторий задач (состояние «не
   исследована») и сразу возвращает управление. Рабочий агент результата не
   ждёт и не читает — он называет находку человеку в ответе.
2. **Исследование** — отдельным фоновым процессом: `claude -p` только на
   чтение (Read, Grep, Glob), без записи, команд и MCP. Перед ним — снимок во
   временной папке: `code/` — последний коммит **основной ветки** репозитория
   (`repos[].branch`, с сервера, если она там есть), `tasks/` — задачи проекта
   с журналами, `findings/` — прежние находки. Рабочая папка агента, её индекс
   и ветка не трогаются.
3. **Сверка.** Ответ модели проверяется механически (`verifyFinding`): каждое
   доказательство — файл, строка, цитата — сверяется со снимком.
4. **Исход.** Подтверждена — задача типа `bug` в статусе `found` (колонка
   «Находки») и вердикт в заметке, одной операцией. Иначе — только вердикт и
   причина в заметке; карточки в Kaiten нет.

## Что считается находкой

Только дефект продукта: продукт делает не то, что должен. Улучшения,
рефакторинг и попутную работу агент называет человеку в ответе и нигде не
заводит. `kaiten new` остаётся для случая, когда задачу попросил завести
человек.

Дефект подтверждён, когда есть всё:

- место в коде основной ветки, где он происходит;
- шаги воспроизведения;
- источник того, как должно быть: тест, документ, задача проекта или явный
  контракт в коде. Источника нет — это улучшение, а не дефект.

**Не подтверждено — значит опровергнуто** (владелец 12.11.2026): в основной
ветке этого нет, не хватило материала (нужен другой репозиторий или живые
данные), цитата не нашлась в файле, задача не прошла проверку формата — всё
это «не подтверждена». Потерять такую находку не страшно.

Повтор уже записанной задачи — вердикт «уже записана» с её именем; в саму
задачу ничего не пишется.

## Задача в «Находках»

- Разделы бага («Что происходит», «Как воспроизвести», «Как должно быть»,
  «Критерии») и «Доказательства»: ветка и коммит, заметка агента, строки кода.
- Разделов для младших (продукт, БД, n8n) исследователь не пишет: это допуск,
  его даёт `npm run assess` или человек после разбора.
- `created_via: agent`, автор — человек, на чьей машине работал агент.
- Из «Находок» задачу выносит человек, переносом карточки в Kaiten.
  `kaiten start` отказывает; с `--assigned` — берёт: прямое поручение человека
  и есть подтверждение (приоритет p0, как у любой неразобранной задачи).
- Отклонить находку — `kaiten cancel`.

«Можно младшему» с 12.11.2026 считается только с «Бэклога»: в «Находках» и во
«Входящих» поле пустое у всех задач (`docs/junior-readiness.md`).

## Очередь и сбои

На машине идёт одно исследование: замок `kaiten-found.lock` в хранилище, очередь
— файлами в `found-queue/`. Заметка вынимается из очереди до запуска модели,
поэтому упавшее исследование само не повторяется.

Исследование не состоялось — нет `claude` на машине, обрыв, ответ не по схеме,
в репозитории нет основной ветки — заметка остаётся «не исследована». Такие
добирает скрипт владельца. Это не то же, что «не подтверждена»: там
исследование прошло и дефект не доказан.

Сбой молчит — рабочему агенту о нём знать незачем, — поэтому о нём говорит
`kaiten doctor`: запускается ли `claude` на машине и сколько находок ждут
проверки.

`KAITEN_FOUND=off` — не исследовать, `inline` — сразу, в процессе команды
(тесты и пробные прогоны).

## Включение

```json
{ "kaiten": { "found": { "model": "claude-opus-5-5" } } }
```

Нет блока — нет ни колонки, ни команды (`kaiten found` отказывает и просит
сказать о дефекте человеку). `model` можно не писать; Haiku не используем.

Порядок: обновить `kaiten` на всех машинах (новый статус старые версии не
читают; `SYNC_VERSION` 6 заставит их обновиться) → блок в `kaiten.json` →
`npm run setup` (план → `--apply`) заводит колонку «Находки» левее «Входящих»
и пишет её id в `mapping.columns.found` → отправить `kaiten.json`. Блок есть, а
колонки в `mapping` нет — команда отказывает.

До `setup --apply` проверьте правила доски для агентского сервера
(`docs/agent-server.md`): он заводит карточки в первой колонке-очереди, если
правила доски не сужают колонки создания (`columns: [Входящие]`). Без этой
строки карточки не-разработчиков пойдут в «Находки».

Место новой колонки задаётся дробным `sort_order` (половина от наименьшего на
доске). На живой доске это ещё не проверено: если Kaiten не примет, `setup`
остановится на этом шаге, а колонку можно завести и перетащить руками —
`setup` найдёт её по названию.

## Скрипт владельца: `npm run found`

```bash
npm run found -- --tasks <адрес> --code acme-app=<папка>            # неисследованные заметки
npm run found -- --tasks <адрес> --code acme-app=<папка> --legacy   # старые задачи агентов
npm run found -- --tasks <адрес> --apply <файл результатов>
```

Без `--apply` — только исследование, отчёт (markdown) и файл результатов
(JSON); ничего не пишется. `--apply` модель не запускает и применяет ровно
файл: несогласны с находкой — удалите её запись.

`--legacy` — задачи, которые агенты завели до находок: открытые, во
«Входящих», без приоритета, `created_via: agent`. Каждая проверяется как
находка. Применение переносит в «Находки» только подтверждённые (сначала
карточку, затем статус в файле, с записью в журнал задачи); остальные остаются
где лежат и перечислены в отчёте — отменить их или оставить, решает владелец.

Папка `--code` может стоять на любой ветке: код берётся из основной.
