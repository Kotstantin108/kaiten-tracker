# План: «Можно младшему» и оценка задач

Статус: этап 1 (признак) и этап 2 (оценка) сделаны и проверены на тестовой
доске. Решения согласованы с владельцем 19.10.2026; решения, принятые при
реализации этапа 2 (20.10.2026), отмечены ниже.

Цель — младшие разработчики видят на доске Kaiten, какие задачи можно брать
безопасно. Признак — ориентир команды разработки: людей вне разработки он не
касается, брать задачу он не запрещает и не разрешает.

## Признак «Можно младшему»

Задача годится младшему, если выполнены все условия:

1. **Актуальна** — постановку правили не раньше `kaiten.junior.maxAgeDays`
   дней назад (по умолчанию 90). Дата правки — поле `revised`: его ставят
   `kaiten new` и `kaiten edit`, а перенос карточки по доске, приоритет, срок,
   отметки пунктов и журнал — нет (владелец 19.10.2026). У задачи без
   `revised` — от `created`. Подтвердить актуальность старой задачи —
   перечитать и поправить постановку. Отдельной отметки «проверено» нет.
2. **Продуктовые решения** — раздел заявляет «нет» либо описывает их полностью.
3. **Изменения в БД** — то же.
4. **Сценарии n8n** — то же.
5. **Оценка** (этап 2) — не «Похоже, сделана» и не «Похоже, устарела».

Значение вычисляет инструмент из файла задачи, механически и без сети. Модель
в вычислении не участвует.

Где признак есть: типы `story`, `tech`, `bug` в статусах `inbox`, `backlog`,
`ready`. У `epic` и `spike` разделов нет. У остальных статусов (задача взята,
заблокирована или закрыта) оба поля пустые: пустое — «не применимо», а не
«нет». Задача, вернувшаяся в бэклог, вычисляется заново.

### Разделы

Три раздела в теле story/tech/bug — после «Что сделать» (у bug — после «Как
должно быть»), перед «Критериями». Заголовки ровно такие:

```markdown
## Продуктовые решения
Нет.

## Изменения в БД
**Что меняется:** таблица orders — новое поле paid_at.
**Миграция:** существующим строкам — NULL, данные не переносятся.
**Откат:** удалить поле, код читает его как необязательное.
**Как проверить:** после оплаты в orders.paid_at — время оплаты.

## Сценарии n8n
Нет — сценарии не затрагиваются.
```

Разбор:

- Тело раздела начинается со слова «Нет» (регистр и точка не важны) — явное
  «нет»; текст после него признак не читает.
- Иначе — «есть»: должны быть все метки вида `**Метка:** текст`, текст
  непустой и не подсказка каркаса (`stripTemplateHints`).
- Нет раздела, подсказка каркаса вместо текста, не хватает метки — признак
  «Нет» с причиной. **Это не отказ**: разделы необязательны, задачу можно
  поставить без них.

Метки по виду:

| Раздел | Метки |
|---|---|
| Продуктовые решения | Что решено · Где зафиксировано · Открытые вопросы |
| Изменения в БД | Что меняется · Миграция · Откат · Как проверить |
| Сценарии n8n | Сценарий · Что меняется · Входы и выходы · Как проверить |

«Открытые вопросы» — единственная метка, где проверяется значение: годится
только «нет». Пункты оформлены строками, а не `- [ ]`: флажки уходят в
чек-листы Kaiten, а это описание, а не работа.

### Поля в Kaiten

| Поле | Вид | Владелец |
|---|---|---|
| Можно младшему | выбор: Да / Нет | инструмент — ручную правку синхронизация возвращает |
| Младшему не хватает | строка, только при «Нет» | инструмент |

Пример строки: «задача старше 90 дней; БД: нет пункта „Откат“; продукт:
есть открытые вопросы». Поле-выбор — для фильтра на доске.

Поля пересчитываются синхронизацией (после записи у любого разработчика и при
`kaiten pull`) и отправляются, только если разошлись с вычисленными. Своего
расписания нет: по возрасту «Да» сменится на «Нет» при ближайшей синхронизации.

### Кто пишет разделы

Только команда разработки — через `kaiten new` и `kaiten edit`. Правка
описания в интерфейсе Kaiten до файла не доходит, и это не меняется.

- Каркас story/tech/bug получает три раздела с подсказками.
- Скилл: ставя задачу, агент заполняет разделы. «Нет» — утверждение: писать
  его, только проверив по коду, что изменений нет; не знает — оставить раздел
  пустым. Ложное «Нет» делает опасную задачу «безопасной».
- Вывод `kaiten new` добавляет строку «Младшему: нет — не хватает: …».
- `kaiten list` и `kaiten show` не меняются: младшие смотрят доску.

### Включение

```json
{ "kaiten": { "junior": { "maxAgeDays": 90 } } }
```

Нет блока — нет ни полей, ни разделов в каркасе, ни строки в `kaiten new`.
`npm run setup` (план → `--apply`) заводит поля, добавляет их типам
story/tech/bug и пишет id в `mapping`; поля компании заводит администратор
компании Kaiten. Блок есть, а id в `mapping` нет — конфиг загружается, поля
не пишутся, `kaiten doctor` и синхронизация говорят «запустите setup».
Шаблон описания типа карточки в Kaiten не трогаем.

## Оценка задач: `npm run assess`

Скрипт владельца. По каждой задаче агент читает постановку, код и сценарии
n8n и выносит вердикт; заодно дописывает три раздела.

### Поле «Оценка»

| Значение | Что значит |
|---|---|
| Актуальна | задачу есть смысл делать; разделы предложены |
| Похоже, сделана | код уже на месте — доказательства в комментарии |
| Похоже, устарела | модуль удалён, сценарий переписан, смысл потерян |

- Выбор в Kaiten, пустой — не оценивали. **Владелец — Kaiten**, как у
  приоритета: скрипт ставит значение при `--apply`, человек, перепроверив,
  меняет его в Kaiten, синхронизация переносит в файл.
- Доказательства — комментарием скрипта в карточке: что проверено, файлы,
  коммиты, сценарии.
- Задачи **закрывает только человек** (`kaiten done` / `kaiten cancel`).
  Вердикты «похоже…» скрипт никогда не применяет к статусу.
- В файле — два поля, у каждого свой владелец: `assessment` — зеркало
  «Оценки» из Kaiten (синхронизация, как приоритет), `assessed: { verdict,
  date }` — что поставил скрипт и когда (только `--apply`). Совпадают —
  оценка скрипта, расходятся — человек поправил её в Kaiten. Оба правятся не
  в тексте задачи: `kaiten edit` их не меняет.
- Зеркало пишется, только когда поле заведено (`mapping.assessProperty`):
  старые версии `kaiten` незнакомого ключа в файле не читают (схема
  строгая). Порядок включения: обновить `kaiten` на всех машинах → `setup`
  → отправить `kaiten.json`.

### Что оценивается

- Только открытые story/tech/bug в `inbox`, `backlog`, `ready`. Архив,
  взятые, на ревью и заблокированные — нет.
- Без оценки, или оценка скрипта старше 90 дней.
- Ручная оценка — никогда; заново — только `--only PRJ-123 --force`.
- «Похоже, сделана/устарела» от скрипта повторно не оценивается: ждёт
  человека.

Цикл: применённая «Актуальна» от скрипта освежает задачу на `maxAgeDays`,
как правка постановки, — и когда разделы дописаны, и когда дописывать было
нечего (возраст — от более поздней из дат `revised` и `assessed.date`,
пока оценку не поправил человек; 20.10.2026). Потом признак становится
«Нет — устарела», и следующий прогон оценивает задачу снова.

### Откуда код и сценарии

```bash
npm run assess -- --tasks <репозиторий задач> --code acme-app=<папка> --code acme-n8n=<папка>
```

- Агент видит репозиторий задачи (поле `repo`) и все общие репозитории —
  `repos[]: { "name": "acme-n8n", "label": "Acme-n8n", "shared": true }` в
  `kaiten.json` (без `lane` — без дорожки на доске). Общий репозиторий
  остаётся обычным репозиторием проекта: задачи с таким `repo` возможны.
  Папки всех общих репозиториев обязательны — без них агент не увидит
  сценариев и напишет ложное «Нет».
- Сделанным считается только то, что в истории текущей ветки папки (обычно
  `main`): правка, лежащая лишь в ветке задачи или в невлитом PR, — ещё не
  сделано (живьём 20.10.2026 агент иначе счёл сделанной невлитую правку).
- Сценарии n8n — файлами (n8n-as-code), не из живого n8n: ни токена n8n, ни
  сети. Перед прогоном владелец обновляет выгрузку сценариев.
- Нет папки для репозитория задачи — задача пропускается строкой в отчёте.

### Агент

- `claude -p` на задачу, только чтение: `--tools Read Grep Glob Bash`,
  разрешены только `git log`/`git show` (в общих репозиториях —
  `git -C <папка> …`), `--strict-mcp-config` без серверов. Ни записи, ни
  MCP, ни Kaiten; запрещённое отклоняется, а не ждёт подтверждения
  (проверено 20.10.2026). Модель по умолчанию — Opus 5.5, `--model` для
  другой; Haiku скрипт не принимает.
- Ответ — JSON по zod-схеме (`--json-schema`, без `$schema`): вердикт,
  обоснование, текст недостающих разделов, доказательства, обоснование
  каждого «Нет». Скрипт просит только разделы, которые признак не
  засчитывает: полный раздел человека не переписывается.
- Проверка до записи: разделы проходят разбор признака (открытые
  продуктовые вопросы — честный ответ: раздел принимается, признак «Нет»);
  каждый файл и сценарий существует в переданных папках, каждый коммит — в
  истории их текущей ветки; путь наружу из папки не принимается; «Нет» без
  обоснования — непроверенное. Не прошёл — «агент не справился» в
  отчёте, без записи и без повтора вслепую.
- `--only PRJ-123`, `--limit N`, `--parallel N`.

### Сухой прогон и применение

- По умолчанию: отчёт (markdown) и файл результатов (JSON) во временной
  папке (`--out` — другая): в них текст задач проекта, а репозиторий
  инструмента публичный. Ничего не пишет.
- `--apply <файл результатов>` применяет ровно этот файл, агента не
  запускает: разделы — правкой задачи, «Оценка» — в Kaiten, доказательства —
  комментарием.
- Несогласен с задачей — удалить её запись из файла и применить остальное.
- Задача изменилась после оценки (хеш постановки), её взяли в работу или у
  неё другая карточка — запись не применяется: «оцените заново».
- На задачу: «Оценка» и комментарий в карточку, затем разделы — операцией
  `edit` (ставит `revised`), затем отметка `assessed`. Всё под замком
  синхронизации: иначе фон прочёл бы оценку в карточке раньше отметки и
  записал бы её как оценку человека. «Можно младшему» в карточке обновит
  ближайшая синхронизация.

### Расписание

Пока нет: сначала несколько ручных прогонов. Следующий шаг — расписание без
применения (Actions делает сухой прогон и выкладывает файл результатов,
применяет владелец). Разделы без человека не применяются никогда.

## Порядок работ

Отдельная ветка на этап. Сначала тестовая доска; живой проект — после «да»
владельца на сухой прогон.

**Этап 1 — признак.**

- Разбор разделов и вычисление признака — чистая функция в `src/core/` с
  тестами: «Нет», полный раздел, нехватка метки, подсказка каркаса,
  «Открытые вопросы» не «нет», возраст, статусы, epic/spike.
- Каркас story/tech/bug — `src/core/skeleton.ts`.
- `kaiten.junior` и id полей в `mapping` — `src/config.ts`.
- Поля в плане `setup` — `src/setup-plan.ts`.
- Запись двух полей в плане синхронизации — `src/core/kaiten-sync-plan.ts`
  (по образцу «Сути»: сравнить с карточкой, отправить разницу).
- Строка в выводе `kaiten new`; проверка в `kaiten doctor`.
- Скилл `skills/kaiten/SKILL.md`, README.
- Включение в настоящем проекте — массовая запись в открытые карточки, и
  начинается она не с `--apply`: как только `kaiten.json` с id полей уйдёт в
  репозиторий задач, поля напишет фоновая синхронизация любого разработчика.
  Поэтому порядок такой: `junior` в рабочей копии → `setup` (план → `--apply`,
  id — в рабочую копию) → сухой прогон
  `kaiten-sync -- --tasks <адрес> --config <рабочая копия>/kaiten.json`
  (строка «Можно младшему»: сколько «Да», «Нет», очистить) → «да» владельца
  → коммит и отправка `kaiten.json`.

**Этап 2 — оценка** (сделано 20.10.2026).

- Поле «Оценка» в `setup`; перенос из карточки в файл (`mirrorFromCard`) и
  учёт, кто поставил; влияние на признак.
- `repos[].shared` в `kaiten.json`.
- `npm run assess`: отбор задач, запуск агента, схема ответа, проверка
  доказательств, отчёт и файл результатов, `--apply`.
- Проверка на тестовой доске, затем `--only` на одной задаче живого проекта.
