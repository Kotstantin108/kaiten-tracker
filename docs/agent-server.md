# Агентский сервер Kaiten (MCP)

Удалённый MCP-сервер, через который агенты не-разработчиков работают с
Kaiten: заводят и ведут задачи, пишут документацию. На ПК людей ничего не
ставится. Сервер не знает ни одного проекта: правила живут в самом Kaiten —
в описаниях досок и на служебных страницах папок документов.

Главный принцип — **отказ до записи**. Всё, что обязательно, сервер
проверяет до запроса в Kaiten и отказывает одним списком: чего не хватает,
какого типа, какие значения допустимы и что поле значит. Агент либо
догадывается сам, либо спрашивает человека — третьего пути нет.

## Клиенты и доступ

- Claude (коннектор), Codex, Cursor, OpenClaw и любой клиент MCP по
  Streamable HTTP.
- Сервер пишет **от имени человека** его личным токеном Kaiten. Работает с
  одной компанией, домен — в настройках сервера.
- Токен Kaiten у клиента не лежит никогда. Человек вводит его на странице
  сервера; сервер шифрует его своим секретом и выдаёт **ключ** — он работает
  только с этим сервером. Отозвать доступ — перевыпустить токен в Kaiten.
- Два пути входа, за обоими один и тот же ключ:
  - OAuth (кнопка «Подключить» в клиенте; динамическая регистрация клиента);
  - заголовок `Authorization: Bearer <ключ>` — для клиентов без браузера.
- Человек видит всё, что видит в Kaiten. Доски разработки защищены членством
  и своими ограничениями Kaiten.

## Запреты на уровне HTTP

Независимо от инструментов, обёртка над `fetch` пропускает в Kaiten только
разрешённые метод и путь. Запрещено всегда:

- любой `DELETE`;
- выдача доступа и участники (`…/users`, `…/groups`, роли) — приглашение по
  почте заводит пользователя компании;
- настройки компании;
- копирование документа (`clone_uid`) и документ без родителя;
- структура: пространства, доски, колонки, дорожки, типы, поля, ограничения.

## Режим «Задачи»

**Можно:** читать и искать карточки, читать правила доски; создавать
карточку; переводить этап или дорожку вместе с полями, которых требует
переход; править поля и описание; комментировать; вести чек-листы; связывать
с родителем; ставить и снимать блокировку.

**Нельзя:** удалять и архивировать; менять ответственного, участников и
сроки после создания; менять структуру. При создании ответственный — сам
человек; другой участник — только если пользователь назвал его прямо.

**Правила создания:**

1. Только в колонки типа «очередь».
2. Обязательные поля типа карточки (настройки типа в Kaiten).
3. Поля, которых требуют ограничения целевой колонки, — сервер проходит те
   же условия, что Kaiten, до записи.
4. Из блока правил доски: шаблон названия по типу, обязательный родитель по
   типу, дорожка по умолчанию, запрет дублей.
5. Дубли: та же доска (настраивается — всё пространство), открытые карточки
   (не в колонке «готово»), сравнение без регистра, лишних пробелов, кавычек,
   ё/е. Совпадение — жёсткий отказ со ссылкой, флага «всё равно создать» нет.
6. Создание в два шага: предпросмотр и подписанный одноразовый код (10 минут,
   привязан к человеку и содержимому); запись — только с кодом.
7. Созданной карточке — метка «агент» и комментарий с исходной просьбой
   пользователя.

**Описание доски** — инструкция для агента и источник правил. Не правится
вручную (об этом сказано в нём самом). Две части:

- текст: «Доска», «Этапы», «Поля» — сервер проверяет, что описаны все
  колонки и все обязательные и требуемые ограничениями поля, и берёт
  пояснения полей в свои отказы;
- блок правил YAML — только то, чего не выражает Kaiten.

Описания нет или оно не разбирается — доска закрыта для записи агентом.

Блок правил (раздел `## Правила`, блок ```` ```yaml ````):

```yaml
version: 1
duplicates: board        # board | space | off
columns: [Входящие]      # необязательно: сузить колонки создания (только очереди)
synced: true             # необязательно: карточки с external_id ведёт git —
                         # агент их только комментирует
types:                   # какие типы можно заводить; "*" — любой тип доски
  Сделка:
    title: "{Клиент} — {Суть}"   # {Часть} — непустой текст, остальное буквально
    lane: choose                 # choose — агент выбирает явно; default — первая
                                 # дорожка доски; иначе — название дорожки
    parent: none                 # или название типа обязательного родителя
```

Ограничения Kaiten сервер проходит сам (семантика снята живьём):
`prevCardPath` перечисляет колонки, *из* которых переносить нельзя;
`childCardsDone` с `eq` выполнено, пока дочерние карточки не готовы.

**Инструменты:** `whoami`, `list_boards`, `board_rules`, `find_cards`,
`get_card`, `create_card` (предпросмотр → `confirm_code`), `move_card`,
`update_card`, `add_comment`, `checklist_item`, `link_parent`, `block_card`.

## Режим «Документы»

Документация живёт в документах Kaiten (дерево папок и страниц).

**Уровни доступа** (по умолчанию; папка может переопределить):

| Уровень | Действия |
|---|---|
| Свободно | читать, искать, создать страницу по шаблону, дописать в раздел, добавить связь |
| С подтверждением человека | заменить раздел, переписать страницу, переименовать, перенести, статус «Действует» и «Устарел», откат, массовая правка |
| Запрещено | удалять страницы и папки, менять структуру папок, трогать папки без правил, менять правила |

**Подтверждение человека** идёт не через агента: сервер возвращает
одноразовую ссылку (30 минут), человек открывает её в браузере, видит
разницу «было → станет» и нажимает «Применить» или «Отклонить». Страница
работает только при входе человека на сервер в браузере.

**Копия перед каждой правкой** хранится на сервере (зашифрована, 30 дней).
Откатить может тот, у кого сейчас есть доступ к странице, — и тоже через
подтверждение.

**Правила папки** — служебная страница «⚙ Правила для агента» в папке: текст
для агента и блок правил YAML (разрешена ли папка, уровни, шаблон разделов,
правило названия, обязательная связь с карточкой). Подпапка наследует правила
родителя. Нет правил — папка только для чтения. Агент служебную страницу не
видит, не создаёт и не правит.

**Структура страницы:**

- шапка, её ведёт сервер: владелец (по умолчанию — кто попросил), статус
  (Черновик → Действует → Устарел), «Связано с» (ссылки на карточки),
  обновлено;
- обязательные разделы шаблона папки — все, по порядку, непустые; свои
  разделы можно добавлять после них;
- «История изменений» — последний раздел, дописывает только сервер.

Страницы, написанные людьми, сервер не требует приводить к шаблону: при
первой правке агентом добавляются только шапка и история.

**Связь с карточками:** ссылки в шапке; сервер сам добавляет в каждую
связанную карточку внешнюю ссылку на документ; папка может требовать
обязательную связь; снимает связь только человек.

**Инструменты:** `list_docs`, `read_doc`, `search_docs`, `create_doc`,
`append_to_section`, `replace_section`, `set_doc_status`, `rename_doc`,
`link_doc`, `doc_versions`, `rollback_doc`. Переноса между папками пока нет.

Блок правил папки — блок кода YAML на странице «⚙ Правила для агента»:

```yaml
version: 1
title: "{Клиент} · установка {Номер} — {Акт}"
sections: [Объект, Что проверено, Результат, Подписи]
link: Установка            # none | тип | [тип, тип]
levels:
  append: free             # free | confirm
  replace: confirm
  locked_when_active: true # после «Действует» — всё с подтверждением
```

Подтверждает человек, вошедший на сервер в браузере: куки ставится, когда
он сам вводит токен Kaiten (страница ключа, подключение по OAuth, страница
входа). Ключ агента входом не считается. Агент, который управляет браузером
человека, этот куки получит вместе с браузером — для такого агента
подтверждение не барьер.

Страницы, написанные людьми в интерфейсе, агент пока только читает: не
проверено, примет ли API правку документа новой схемы.

## Что важно знать о документах Kaiten

- Содержимое пишется только целиком (ProseMirror JSON), блокировки нет —
  последняя запись выигрывает. Сервер перечитывает страницу перед записью и
  отказывает, если она изменилась.
- Документ, созданный через API, получает старую схему: без чек-листов,
  ссылок-карточек и вкладок.
- Правки через API не попадают в историю версий Kaiten — отсюда собственные
  копии сервера.

## Размещение

Cloudflare Workers + KV (OAuth и копии страниц). Ядро на стандартных
Request/Response, без Durable Objects — чтобы переехать на свой сервер. Об
облаке знает только входной файл. Секреты — `wrangler secret`; домен
компании, идентификаторы аккаунта и адрес сервера в репозиторий не попадают.

## Порядок

1. Сервер на тестовом пространстве: сначала проверка, что Kaiten принимает
   запросы из Cloudflare и что вход по OAuth проходит до конца.
2. Описания для всех существующих досок и правила папок — черновики
   владельцу, в Kaiten только после «да».
3. Пилот — владелец один.
4. Ежедневный срез и восстановление; затем боевое пространство.
