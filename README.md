# kaiten-tracker

Синхронизатор задач между базой задач и Kaiten. Сейчас умеет разовую заливку
(`import`), дальше из него вырастает двусторонний цикл сверки.

Схема из трёх репозиториев (Q17, Q36–Q38): код проектов, **база задач** (файлы
задач всех проектов) и этот воркер. Разделение — ради радиуса поражения: git не
умеет прав на подпапку, поэтому ключ на запись задач не должен открывать код и
путь в прод. Доступа к репозиториям кода у воркера нет вовсе.

Ни одно поле не имеет двух владельцев: тело задачи и `LOG.md` принадлежат базе
задач, сроки, исполнители и очередь — Kaiten, а `in-progress/review/done`
приезжают штатной интеграцией Kaiten ↔ GitHub, мимо воркера.

⚠️ Базы задач ещё не существует: она создаётся в story `export-csv`. Пока
импортёр читает старую раскладку `tasks/` репозитория кода — только на чтение и
только для пилота. Что именно придётся переделать, перечислено в `PROMPT.md`.

## Запуск

```bash
npm install
cp .env.example .env          # KAITEN_DOMAIN и KAITEN_TOKEN

npm run inspect               # снимок структуры аккаунта → tmp/import/
# по снимку заполнить блок kaiten в tracker.config.json

npm run import -- --scope pilot --epic reports      # план, ничего не пишет
npm run import -- --only acme-app:20260916_export-csv --apply
```

Без `--apply` не делается ни одной записи. Без токена скрипт работает офлайн:
строит план по локальным файлам и говорит, что состояние аккаунта неизвестно.

## Что где

| Файл | Ответственность |
|---|---|
| `src/task-source.ts` | Обход `tasks/` репозиториев, разбор шапки `TASK.md`, статус из папки, ключ `external_id` |
| `src/kaiten-client.ts` | HTTP-клиент Kaiten: Bearer, пагинация, лимиты, ретраи |
| `src/plan.ts` | Чистое построение плана: создать / обновить / не трогать / связать |
| `src/import.ts` | CLI заливки |
| `src/inspect.ts` | Снимок структуры аккаунта, по нему заполняется маппинг |
| `tracker.config.json` | Репозитории-источники и маппинг доски Kaiten |

## Ключ идемпотентности

`external_id` карточки = `<repo>:<YYYYMMDD>_<slug>`, например
`acme-app:20260916_export-csv`.

Имя репозитория — потому что воркер читает несколько репозиториев. Дата и slug —
потому что это единственное, что у задачи не меняется: папка меняется при смене
статуса, тип и приоритет меняет триаж (`inbox/` → `backlog/<type>/`). Голый slug
не уникален даже внутри одного репозитория.

## Проверки

```bash
npm run typecheck
npm test          # сети в тестах нет: клиент проверяется на поддельном fetch
```

Тест `repo-invariants` проверяет живые репозитории из `tracker.config.json`
(каждая папка разбирается, ключи уникальны) и пропускается, если рабочих копий
рядом нет.
