# kaiten-tracker

Синхронизатор задач между базой задач и Kaiten. Сейчас умеет разовую заливку
(`import`), дальше из него вырастает двусторонний цикл сверки.

Схема из трёх репозиториев (Q17, Q36–Q38): код проектов, **база задач** (файлы
задач всех проектов) и этот воркер. Разделение — ради радиуса поражения: git не
умеет прав на подпапку, поэтому ключ на запись задач не должен открывать код и
путь в прод. Доступа к репозиториям кода у воркера нет вовсе.

Ни одно поле не имеет двух владельцев: тело задачи и `LOG.md` принадлежат базе
задач, сроки, исполнители и очередь — Kaiten, а `in-progress/review/done`
приезжают штатной интеграцией Kaiten ↔ GitHub, мимо воркера.

⚠️ Базы задач ещё не существует: она создаётся в story `export-csv`. Пока
импортёр читает старую раскладку `tasks/` репозитория кода — только на чтение и
только для пилота. Что именно придётся переделать, перечислено в `PROMPT.md`.

## Запуск

```bash
npm install
cp .env.example .env          # KAITEN_DOMAIN и KAITEN_TOKEN

npm run inspect               # снимок структуры аккаунта → tmp/import/
npm run setup                 # план структуры под схему эпика, ничего не пишет
npm run setup -- --apply      # завести недостающее и записать блок kaiten в конфиг

npm run import -- --scope pilot --epic reports      # план, ничего не пишет
npm run import -- --only acme-app:20260916_export-csv --apply
```

CLI задач для агентов и разработчиков (чтение — без сети; запись — сразу
локально, общим — в фоне):

```bash
npm link                      # команда kaiten в PATH
kaiten list                   # открытые задачи продукта текущего репозитория
kaiten show PRJ-123            # задача целиком, её эпик и соседние задачи
kaiten search таймаут вебхук  # по словам, в открытых и закрытых
kaiten files PRJ-123           # вложения задачи
kaiten pull                   # свежие задачи проекта и отправка своих изменений
kaiten new "Починить…" --type bug --summary "…" [--agent]
kaiten check PRJ-123 "тест на таймаут"   # отметить пункты
kaiten log PRJ-123 "что сделано"         # запись в журнал задачи
kaiten block PRJ-123 --reason "…"        # задача заблокирована
kaiten cancel PRJ-123 --reason "…"       # отменить (только не начатую)
kaiten edit PRJ-123            # правка текста в своём редакторе; --stdin — для агента
```

CLI — единственный путь к задачам. Хранилище на машине — git без рабочей
копии (`%LOCALAPPDATA%\kaiten\<tasksRepo>.git`, см. `src/task-store.ts`):
файлов задач на диске нет, и вывод CLI не называет, где они лежат.

**Репозиторий кода подключается файлом `.kaiten`** в корне (кладёт владелец
проекта):

```yaml
project: acme
repo: acme-app
```

Нет файла — команды отвечают «репозиторий не подключён к kaiten». Флага
проекта нет, по имени папки или `origin` проект не угадывается.

**Настройки** — `kaiten.settings.json` рядом с `tracker.config.json`, у
каждого свои (в `.gitignore`; образец — `kaiten.settings.example.json`):
личный вход в Kaiten (`kaiten.domain`, `kaiten.token` — для команд записи)
и копия задач для чтения (`localCopy`: по умолчанию выключена; включённая
лежит в `<dir>/<проект>` и обновляется при каждом `kaiten pull`; файлы
только для чтения, в папку внутри репозитория git не пишется). Ещё способ
читать задачи папками — репозиторий задач на GitHub.

Пробные прогоны — с `KAITEN_STORE`, `KAITEN_CONFIG` и `KAITEN_SETTINGS`,
чтобы не трогать настоящее хранилище и настройки.

Без `--apply` не делается ни одной записи. Без токена скрипт работает офлайн:
строит план по локальным файлам и говорит, что состояние аккаунта неизвестно.

## Что установлено живьём в Kaiten (23–24.09.2026)

- Фильтр `GET /cards?external_id=` — точное совпадение (префикс и ключ с лишним
  символом не находят ничего). Архивные карточки фильтр и список доски отдают.
- Хеш-маркер `<!-- kaiten-sync:… -->` переживает сохранение и правку в интерфейсе.
- Markdown-чекбоксы описание **не отображает**, а редактор при правке экранирует
  их в `\[ \]`. Поэтому пункты уезжают в нативные чек-листы: по чек-листу на
  раздел, в описании — ссылка. Чек-листы создаются один раз и потом только
  дополняются недостающим по имени и тексту; отметки ставят в Kaiten.
- Колонку импорт ставит только при создании карточки: дальше статусом владеет
  Kaiten (Q30), и повторная заливка не должна тащить карточку обратно.
- Связь «эпик → story» видна не всегда с обеих сторон (после архивации эпика у
  story пропадает родитель, у эпика ребёнок остаётся), и архивную карточку можно
  сделать родителем, только если она в «готово».
- Типы карточек и пользовательские поля заводит только администратор компании
  (роль в пространстве не даёт прав на них).
- Всплеск записей обрывался сетевой ошибкой ниже заявленных 50 rps — массовые
  команды идут с паузой 150 мс, чтение после обрыва повторяется, запись — нет.

## Разовая выгрузка yonote

```bash
npm run yonote                  # разведка: списки и счётчики, тексты не качает
npm run yonote -- --download    # тексты, базы данных, комментарии → tmp/yonote/
```

ENV: `YONOTE_DOMAIN`, `YONOTE_TOKEN`. Только чтение, в консоль — только числа
(в корпоративной вики бывают ПДн). Выгрузка лежит в `tmp/` и в git не попадает;
куда её класть, решает владелец, не в репозиторий кода (Q4).

Что установлено живьём 23.09.2026:

- `documents.list` без явного `type` прячет строки баз данных: 149 документов
  против 438. Задачи в yonote вели **строками баз данных** со свойствами
  status/person/people/date, а не чек-листами. Выгрузка кладёт каждую базу в
  `databases/<id>.csv` и `.json`.
- Поле `text` — почти голый текст, без ссылок, картинок и таблиц, а
  `documents.export` создаёт серверную операцию экспорта вместо markdown.
  Полноценный markdown с вложениями даёт только штатный экспорт пространства
  под админом.
- Доски (whiteboard) через API не выгружаются.

## Ключ идемпотентности

`external_id` карточки = `<repo>:<YYYYMMDD>_<slug>`, например
`acme-app:20260916_export-csv`.

Имя репозитория — потому что воркер читает несколько репозиториев. Дата и slug —
потому что это единственное, что у задачи не меняется: папка меняется при смене
статуса, тип и приоритет меняет триаж (`inbox/` → `backlog/<type>/`). Голый slug
не уникален даже внутри одного репозитория.

## Проверки

```bash
npm run typecheck
npm test          # сети в тестах нет: клиент проверяется на поддельном fetch
```

Тест `repo-invariants` проверяет живые репозитории из `tracker.config.json`
(каждая папка разбирается, ключи уникальны) и пропускается, если рабочих копий
рядом нет.
