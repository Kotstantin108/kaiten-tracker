# AGENTS.md

## Что это за репозиторий

Синхронизатор задач «файлы в git ↔ Kaiten» — третий репозиторий схемы (Q17, Q37):
код проектов, база задач и воркер разнесены, чтобы ключ на запись файлов задач не
открывал ни код, ни путь в прод через хостинг.
**Решения Q1–Q42 в карточке эпика — источник истины по архитектуре**
(`../acme-app/tasks/backlog/epics/20260916_epic_p1_reports/`).
Прежде чем предлагать другую схему владения полями, другой ключ или вебхуки
вместо цикла сверки, прочитайте их: почти всё уже разобрано и решено с владельцем.

Целевой источник задач — **база задач** (отдельный репозиторий, папка на проект,
внутри `active/` и `archive/YYYY-MM/`). Импортёр пока читает старую раскладку
репозитория кода, потому что базы задач ещё нет; это временно, см. `PROMPT.md`.

Стек: TypeScript + tsx + zod + vitest. Ничего лишнего: ни фреймворка, ни ORM.

## Правила

- **Ничего не пишем в Kaiten без `--apply`.** Dry-run — поведение по умолчанию у
  любой новой команды, а не опция.
- **У воркера нет доступа к репозиториям кода** — ни ключа, ни записи (Q38).
  Статусы `in-progress`/`review`/`done` ставят команды CLI разработчика
  (`kaiten start/review/done`), интеграции Kaiten ↔ GitHub нет (владелец 29.09).
  Решение, которому нужен доступ к коду, неверное.
- **Мутации живого аккаунта — только после явного «да» владельца.** Это относится
  и к заливке, и к массовым обновлениям карточек.
- **Строгая типизация, `any` запрещён.** Ответы внешнего API разбираются через
  zod; схемы `passthrough()` и описывают только те поля, которые мы читаем —
  структура карточки Kaiten задокументирована не целиком.
- **В тестах нет сети.** Клиент проверяется на поддельном `fetch`.
- **Токен не печатается никогда** — ни в логах, ни в отчётах, ни в URL.
- Комментарии и сообщения коммитов — по-русски, как в основном репозитории.
- Формат коммита: `feat(slug): описание`, `fix(slug): …`, `docs(slug): …`.

## Чего в этом репозитории не делаем

- Не редактируем ничего за пределами базы задач. Сейчас заливка вообще только
  читает: обратная запись (`tracker: PRJ-123` во frontmatter) появится вместе с
  форматом задач v2 и базой задач.
- Не двигаем файлы задач руками: перемещение `active/` ↔ `archive/YYYY-MM/` —
  работа синхронизатора и только его (Q42), иначе папка снова станет вторым
  хранилищем статуса.
- Не тащим в Kaiten `LOG.md` и вложения: они остаются в git, в карточке остаётся
  ссылка.
- Не строим синхронизацию на вебхуках: у Kaiten не опубликованы ни список
  исходящих событий, ни подпись, ни ретраи (проверено 23.09.2026). Цикл сверки
  устойчив к потере события по определению.
